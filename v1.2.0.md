# Spec de Implementação — Melhoria de Gameplay PvP v1.2.0

## 1. Resumo

Versão focada exclusivamente em melhorar a jogabilidade PvP do Rune Wars: mapas maiores e mais complexos, sistema de movimentação com orçamento por turno baseado em agilidade, colisão lateral de terreno ao caminhar, morte por queda em abismos, pontos de spawn seguros, direcionamento de mira e sprite conforme o sentido de movimento.

---

## 2. Pedido Original

> Os mapas existentes são muito pequenos, simples, sem background, sem validação de terreno (pode se mover atravessando paredes), sem limites, sem quedas letais. A v1.2.0 deve focar somente na melhoria da jogabilidade PvP: mapas maiores com 12+ pontos de início, movimentação por orçamento de pixels por turno baseado em agilidade, mira e sprite espelhados conforme direção de movimento. Refazer todos os 5 mapas PvP e os 3 de dungeon.

---

## 3. Problema a Resolver

| # | Problema atual | Impacto |
|---|---|---|
| 1 | Mapas 2000×800px — pequenos para 4v4 | Players muito próximos, sem espaço estratégico |
| 2 | Sem colisão horizontal ao andar | Player atravessa paredes |
| 3 | Sem morte por queda | Cavar abismo não elimina adversário |
| 4 | Sem pontos de spawn definidos | Player pode iniciar dentro de parede |
| 5 | Movimento ilimitado por turno | Quebra balanceamento |
| 6 | Mira e sprite não refletem direção | Feedback visual errado |
| 7 | Sem backgrounds nos mapas | Experiência visual pobre |

---

## 4. Objetivo da Implementação

- Mapas grandes (6000×1600px padrão) com 12 pontos de spawn seguros, terreno rico e backgrounds
- Sistema de movimentação com orçamento de pixels por turno calculado pela agilidade do personagem
- Colisão lateral: personagem para ao encontrar parede sólida
- Morte por queda: personagem que cai além do limite inferior do mapa é eliminado
- Mira e sprite espelhados conforme última direção de movimento

## 6. Pesquisa e Referências

### O que foi pesquisado
- Worms Armageddon / Worms W.M.D. (mapas e sistema de movimento por turno)
- Shellshock Live (orçamento de movimento por atributo)
- Scorched Earth (mapas grandes, física de queda)
- Melhores práticas de design de mapas para artillery games turn-based

### Pontos relevantes encontrados
- Artillery games com 4v4 usam tipicamente mundos de 4000–8000px de largura
- "Worm budget" — orçamento de movimento é a mecânica padrão do gênero; Worms usa ~40px/turno sem boost e até ~600px com haste boots
- Spawn seguro = ponto pré-definido acima de terreno sólido, fora de área de risco
- Colisão horizontal = checar se a célula na direção de movimento é sólida ANTES de mover
- Queda letal = se não há chão dentro de N pixels abaixo do mapa, o personagem morre
- Sprite flip = Phaser suporta `setFlipX(true/false)` nativo em `Image` e `Sprite`

### O que será aproveitado
- Orçamento de movimento por turno com tracker de pixels restantes
- Colisão lateral pré-movimento
- Detecção de abismo: `getFloorBelow` retornando `null` → morte
- 12 spawn points pré-definidos por mapa
- Sprite flip via `setFlipX` (requer migração de `Rectangle` para `Image`)
- Mapas maiores: 300×80 células = 6000×1600px

### O que foi descartado e por quê
- Camera parallax complexa: fora do escopo v1.2.0
- Animações de walk frame-by-frame: fora do escopo, usar flip de sprite estático
- Pathfinding de IA para novo tamanho de mapa: v1.3.0+

## 8. Cálculos de Movimentação

### Parâmetros base
- Largura do mapa: **6000px**
- Agilidade mínima: **0** → 2% de 6000 = **120px por turno**, em 3s → velocidade = **40 px/s**
- Agilidade máxima: **500** → 35% de 6000 = **2100px por turno**, em 5s → velocidade = **420 px/s**

### Fórmulas

```typescript
// Velocidade de movimento em px/s
function moveSpeed(agility: number): number {
  return 40 + (420 - 40) * (agility / 500);  // 40 a 420 px/s
}

// Orçamento total de pixels por turno
function moveBudget(agility: number): number {
  return 120 + (2100 - 120) * (agility / 500);  // 120 a 2100 px
}
```

### Tabela de referência

| Agilidade | Velocidade (px/s) | Orçamento (px) | % do mapa |
|-----------|-------------------|----------------|-----------|
| 0         | 40                | 120            | 2,0%      |
| 50        | 78                | 318            | 5,3%      |
| 100       | 116               | 516            | 8,6%      |
| 200       | 192               | 912            | 15,2%     |
| 300       | 268               | 1308           | 21,8%     |
| 400       | 344               | 1704           | 28,4%     |
| 500       | 420               | 2100           | 35,0%     |

### Implementação por turno

```typescript
// Controle de orçamento durante o turno do jogador
private moveBudgetTotal = 0;       // definido no início do turno
private moveBudgetUsed = 0;        // acumulado durante o turno

// No início de cada turno do jogador:
this.moveBudgetTotal = moveBudget(this.playerAgility);
this.moveBudgetUsed = 0;

// Ao mover:
const remaining = this.moveBudgetTotal - this.moveBudgetUsed;
const actualDelta = Math.sign(deltaX) * Math.min(Math.abs(deltaX), remaining);
this.moveBudgetUsed += Math.abs(actualDelta);
```

## 9. Sistema de Rampa (Step Climbing)

### Regra
Ao tentar mover horizontalmente, se o terreno na direção de movimento tiver uma diferença de altura ≤ **20% do tamanho do personagem**, o personagem sobe ou desce suavemente (rampa). Se a diferença for maior, o movimento é bloqueado — seria necessário pular (fora do escopo v1.2.0).

### Cálculo
- Altura do personagem: **60px**
- Máximo de step: 20% × 60 = **12px**
- 1 célula do grid = 20px → o personagem **não consegue subir 1 célula cheia**, mas consegue subir se a diferença for ≤ 12px (subpixel entre células adjacentes com desnível parcial)

### Implementação

```typescript
private tryMoveHorizontal(deltaX: number): void {
  const direction = Math.sign(deltaX);
  const charHalfWidth = 20;
  const charHeight = 60;
  const MAX_STEP = charHeight * 0.20; // 12px

  const currentFloorY = this.terrainEngine.getFloorBelow(
    this.playerSprite.x, this.playerSprite.y + charHeight / 2
  ) ?? this.playerSprite.y + charHeight / 2;

  const nextX = this.playerSprite.x + deltaX;
  const nextFloorY = this.terrainEngine.getFloorBelow(
    nextX, this.playerSprite.y + charHeight / 2
  );

  if (nextFloorY === null) {
    // Borda do mapa ou abismo — não mover
    return;
  }

  const heightDiff = nextFloorY - currentFloorY; // positivo = descer, negativo = subir

  if (heightDiff < -MAX_STEP) {
    // Subida muito íngreme — bloqueado (precisa de pulo)
    return;
  }

  // Descida suave OU subida ≤ 12px → mover e ajustar Y
  this.playerSprite.setX(nextX);
  const targetY = nextFloorY - charHeight / 2;
  this.playerSprite.setY(targetY);
}
```

### Comportamento visual
- Subida suave: sprite sobe incrementalmente frame a frame (já coberto pelo `CharacterFall` que snappa ao floor)
- Descida suave: sprite desce suavemente pela gravidade existente
- Bloqueio por parede alta: o sprite simplesmente para, sem "escalar"

## 10. Sistema de Colisão Horizontal

**Problema atual:** `movePlayer` soma `deltaX` direto sem verificar se há sólido na direção.

**Solução:** Antes de mover, checar se a célula vizinha na direção X está ocupada.

```typescript
private canMoveHorizontal(fromX: number, fromY: number, direction: number): boolean {
  const charHeight = 60; // altura do sprite em px
  const charHalfWidth = 20;
  const checkX = fromX + direction * (charHalfWidth + 2); // 2px de margem

  // Checar em 3 pontos verticais (topo, meio, base) do personagem
  const checkPoints = [
    fromY - charHeight / 2 + 4,   // topo (com margem)
    fromY,                          // meio
    fromY + charHeight / 2 - 4,   // base (com margem)
  ];

  for (const checkY of checkPoints) {
    const mat = this.terrainEngine.getMaterialAt(checkX, checkY);
    if (mat !== TerrainMaterial.EMPTY) return false;
  }
  return true;
}
```

## 10. Sistema de Morte por Queda

**Problema atual:** `getFloorBelow` retornando `null` → personagem para no lugar.

**Solução em `CharacterFall`:**

```typescript
// Adicionar propriedade de rastreamento
private fallDurationMs = 0;
private readonly FALL_DEATH_THRESHOLD_MS = 3000; // 3s sem chão = morte

update(sprite, engine, dt): 'alive' | 'dead' {
  const floorY = engine.getFloorBelow(sprite.x, feetY);

  if (floorY === null) {
    this.isFalling = true;
    this.fallDurationMs += dt;
    sprite.setY(sprite.y + FALL_SPEED * (dt / 1000)); // continua caindo

    if (sprite.y > engine.worldHeight + 100 || this.fallDurationMs > FALL_DEATH_THRESHOLD_MS) {
      return 'dead';
    }
    return 'alive';
  }

  this.fallDurationMs = 0;
  // ... lógica existente de snap ao floor
  return 'alive';
}
```

Em `BattleScene.update()`:
```typescript
const playerResult = this.playerFall.update(this.playerSprite, this.terrainEngine, delta);
const aiResult = this.aiFall.update(this.aiSprite, this.terrainEngine, delta);

if (playerResult === 'dead') this.onCharacterDeath('player');
if (aiResult === 'dead') this.onCharacterDeath('ai');
```

### Física com facing
O ângulo exibido sempre é relativo ao facing. Na hora de disparar:

```typescript
private getWorldAngle(angle: number, facing: 'left' | 'right'): number {
  // angle: 5-175 relativo ao facing
  // Facing right: ângulo direto (45° = up-right)
  // Facing left: espelhar (45° = up-left → 180 - 45 = 135° no sistema global)
  return facing === 'right' ? angle : 180 - angle;
}
```

O `ProjectilePhysics.simulate()` recebe o ângulo global — sem mudança interna.

### HUD de ângulo
- Exibir `← ${angle}°` quando facing left e `${angle}° →` quando facing right
- Indicador de trajetória inicia na posição do sprite apontando para o lado correto

## 12. Renderização de Mapas como Imagem (Estilo DDTank / Gunbound)

### Problema atual
O terreno é renderizado como retângulos coloridos de 20×20px empilhados. O resultado é visual blocado e sem apelo artístico.

### Solução: Arquitetura em duas camadas

O grid de colisão (20px células) **permanece intacto** como fonte de verdade para física. O que muda é **apenas a camada visual**: o terreno é desenhado como textura contínua usando `Phaser.GameObjects.RenderTexture`, com imagens de tiles que dão aparência de terreno pintado.

```
┌─────────────────────────────────┐
│  Layer 3: Sprites / Projéteis   │  depth 5+
│  Layer 2: Terrain RenderTexture │  depth 2  ← NOVO (substitui TerrainRenderer atual)
│  Layer 1: Background Image      │  depth 0  ← NOVO (arte de fundo por mapa)
└─────────────────────────────────┘
```

### Camada 1 — Background (imagem de fundo)
- Cada mapa tem um PNG de fundo (`bg_plains.png`, `bg_castle.png`, etc.)
- Posicionado em `(0, 0)`, tamanho `worldWidth × worldHeight`, `depth = 0`
- **Não é afetado por explosões** — é puramente decorativo (céu, montanhas distantes, etc.)
- Dimensões: 6000×1600px (ou gerado por tile repetido via `setTileScale`)

### Camada 2 — Terrain RenderTexture (terreno destrutível)
- Um `RenderTexture` de `worldWidth × worldHeight` pixels, `depth = 2`
- Inicializado desenhando **tiles de textura** sobre cada célula sólida do grid
- Cada tipo de material tem um tile diferente:
  - `DESTRUCTIBLE` → textura de terra/pedra/madeira (conforme mapa)
  - `INDESTRUCTIBLE` → textura de rocha/pedra mais escura e detalhada
  - `CONSTRUCTED` → textura de bloco rúnico brilhante (já existente)

```typescript
// terrain-renderer.ts — novo método
renderFull(): void {
  this.rt.clear();
  for (let row = 0; row < GRID_ROWS; row++) {
    for (let col = 0; col < GRID_COLS; col++) {
      const mat = this.engine.getGrid()[row][col];
      if (mat === TerrainMaterial.EMPTY) continue;
      const tileKey = this.getTileKey(mat); // e.g. 'tile_plains_dirt'
      this.rt.drawFrame(tileKey, 0, col * CELL_SIZE, row * CELL_SIZE);
    }
  }
}
```

### Explosões no RenderTexture
Quando células são destruídas, apagar os pixels do `RenderTexture` usando o blend mode `ERASE`:

```typescript
updateCells(destroyed: TerrainCell[]): void {
  // Apagar áreas destruídas do RenderTexture usando círculo de erase
  this.rt.beginDraw();
  for (const cell of destroyed) {
    // Desenhar um círculo preto com blend ERASE na posição da célula
    this.eraseCircle(cell.x * CELL_SIZE, cell.y * CELL_SIZE, CELL_SIZE);
  }
  this.rt.endDraw();
}
```

Isso cria o efeito de "buracos" no terreno visualmente, idêntico ao estilo DDTank/Gunbound.

### Assets de tiles necessários por mapa

| Mapa | Tile Destrutível | Tile Indestrutível | Background |
|------|-----------------|-------------------|------------|
| Plains | `tile_plains_dirt.png` (32×32) | `tile_plains_rock.png` | `bg_plains.png` |
| Castle | `tile_castle_stone.png` | `tile_castle_bedrock.png` | `bg_castle.png` |
| Deep Mines | `tile_mines_earth.png` | `tile_mines_rock.png` | `bg_mines.png` |
| Arcane Ruins | `tile_ruins_stone.png` | `tile_ruins_pillar.png` | `bg_ruins.png` |
| Runic Forest | `tile_forest_wood.png` | `tile_forest_trunk.png` | `bg_forest.png` |
| Dungeon (3 mapas) | `tile_dungeon_rock.png` | `tile_dungeon_wall.png` | `bg_dungeon.png` |

Todos os tiles: **32×32px** (renderizados em células de 20px via `drawFrame` com escala ou tiles menores repetidos).

> **Nota:** Para v1.2.0, os backgrounds e tiles podem ser artes simples/placeholder (gradientes, padrões repetitivos) criados via código Phaser (Graphics + generateTexture) caso os assets artísticos finais ainda não estejam prontos. A arquitetura já estará no lugar para substituir pelas artes definitivas na v1.3.0.

### Impacto no `TerrainRenderer`
- Substituir `add.rectangle()` por `RenderTexture`
- `renderFull()` → redesenha todas as células com tiles
- `updateCells()` → apaga células destruídas via ERASE blend mode
- Manter a interface pública idêntica — `BattleScene` não precisa mudar nada além de passar o mapa correto

### Spawn Points por Mapa
Cada mapa deve ter array `spawnPoints: Array<{col: number, row: number}>` com 12 pontos, todos sobre terreno sólido, espaçados para evitar conflito de posição inicial.

Regras de spawn seguro:
- Célula imediatamente abaixo do ponto deve ser sólida (não EMPTY)
- Raio de 5 células em torno não pode ter outro spawn
- Pelo menos 3 spawns por "lado" do mapa (esquerda, centro-esq, centro-dir, direita)

### Atribuição aleatória de spawn
Os 12 pontos são **fixos no mapa** (posições seguras garantidas pelo design), mas **qual jogador cai em qual ponto é sempre sorteado aleatoriamente** a cada partida ou reinício. Isso garante imprevisibilidade e rejoga diferente mesmo no mesmo mapa.

```typescript
// spawn-selector.ts
export function selectSpawns(
  spawnPoints: Array<{ col: number; row: number }>,
  playerCount: number
): Array<{ col: number; row: number }> {
  // Shuffle Fisher-Yates e retorna os N primeiros
  const shuffled = [...spawnPoints];
  for (let i = shuffled.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [shuffled[i], shuffled[j]] = [shuffled[j], shuffled[i]];
  }
  return shuffled.slice(0, playerCount);
}
```

Chamada em `BattleScene.create()`:
```typescript
const spawns = selectSpawns(mapMeta.spawnPoints, 2); // 2 = jogador + IA
// spawns[0] → jogador, spawns[1] → IA
```

A cada `resetBattle()` ou `scene.restart()`, o sorteio é refeito — nunca os mesmos pontos na mesma ordem.

### Descrição de cada mapa redesenhado

#### 1. Plains (Planícies)
- Terreno: solo plano com colinas suaves no centro e nas bordas
- Características: 3 plataformas elevadas de terra destrutível distribuídas no centro-esquerda, centro e centro-direita; fossos de 4-6 células de largura nos terços; solo base a ~row 65
- Abismos: 4 fossos estrategicamente posicionados para penalizar posicionamento ruim
- Background: céu azul com nuvens (gradient ou imagem de fundo)
- Bordas: paredes indestrutíveis nas colunas 0-2 e 298-299
- 12 spawns: 3 por quadrante (esquerda alta, esquerda baixa, centro-esq, centro-dir, direita alta, direita baixa, etc.)

#### 2. Castle (Castelo)
- Terreno: estrutura de castelo com torres, paredes, muralhas, fosso central
- Características: 2 torres altas indestrutíveis nas bordas esquerda/direita; muralha central com portão (gap de 5 células); plataformas de pedra destrutíveis escalonadas
- Abismos: fosso central (20 colunas, water/void); buracos nas muralhas
- Background: céu noturno com lua
- Bordas: paredes de castelo indestrutíveis

#### 3. Deep Mines (Minas Profundas)
- Terreno: cavernas com pilares verticais, teto parcial, poços profundos
- Características: teto de pedra indestrutível nas rows 0-5 (com buracos); colunas de pedra a cada ~40 colunas; chão irregular com poços que matam
- Abismos: 6 poços profundos (largura 3-8 células, profundidade completa)
- Background: pedra escura com veios de minério
- Bordas: paredes de rocha indestrutíveis

#### 4. Arcane Ruins (Ruínas Arcanas)
- Terreno: ruínas de templo com plataformas suspensas, arcos, pilares
- Características: plataformas flutuantes de pedra destrutível em alturas variadas; pilares indestrutíveis; rampas de escombros
- Abismos: void entre as plataformas — cair entre plataformas = morte
- Background: céu mágico roxo com partículas
- Bordas: barreira de energia (indestrutível)

#### 5. Runic Forest (Floresta Rúnica)
- Terreno: plataformas de galhos e raízes; terreno orgânico com muita verticalidade
- Características: 4 árvores-plataforma em colunas alternadas (com topo destrutível); raízes como plataformas baixas; rampas de terra suave
- Abismos: entre as raízes das árvores há void (queda letal)
- Background: floresta verde densa com luz filtrada

#### 6. Dungeon — Cave Entrance
- 200×60 células = 4000×1200px (menor que PvP por ser PvE solo/duo)
- Estrutura: entrada de caverna, corredor amplo, teto baixo nos extremos
- 6 spawn points (apenas lado esquerdo para jogadores, direito reservado para inimigos)

#### 7. Dungeon — Cave Hall
- 200×60 células
- Grande salão com pilares centrais, stalagmites, stalactites indestrutíveis
- 6 spawn points jogador (lado esquerdo)

#### 8. Dungeon — Cave Boss
- 200×70 células
- Arena fechada com fundo plano, paredes altas, plataformas laterais
- 4 spawn points jogador (centro-esquerda)
