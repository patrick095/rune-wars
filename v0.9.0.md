# v0.9.0 — Backend Mínimo e Multiplayer PvP

> **Status:** Planejado
> **Fase:** 10 + 11 — Persistência Real e PvP Online
> **Depende de:** [v0.8.0](./v0.8.0.md)
> **Objetivo:** Conectar NestJS + PostgreSQL + Redis, migrar o personagem do localStorage para o banco, e implementar PvP 1v1 real com WebSocket e servidor autoritativo.

---

## 1. Resumo

Esta versão é o ponto de inflexão do projeto: tudo que foi validado localmente começa a ter persistência real e jogadores reais podem se enfrentar. NestJS entra como backend autoritativo para turno, vento, dano e terreno. O personagem migra do localStorage para o banco. O PvP usa WebSocket com sala 1v1 e reconexão básica.

---

## 2. Objetivo da Entrega

### Backend Mínimo

- NestJS com PostgreSQL e Redis.
- Autenticação básica (email + senha, JWT).
- CRUD de personagem.
- Persistência de inventário simples.
- Persistência de progresso de dungeon (Andar 1).
- Migração de dados do localStorage (ao fazer login pela primeira vez).

### Multiplayer PvP

- WebSocket com sala 1v1.
- Backend autoritativo para: turno, vento, dano, terreno, efeitos rúnicos.
- Reconciliação: client prevê visualmente, servidor confirma.
- Matchmaking simples (fila FIFO por força de combate aproximada).
- Reconexão: sala fica ativa por 60s aguardando jogador voltar.
- Replay/debug de eventos da partida (log de ações).

## 4. Entidades de Banco de Dados

### User

```sql
CREATE TABLE "user" (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email VARCHAR(255) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  created_at TIMESTAMP DEFAULT NOW()
);
```

### Character

```sql
CREATE TABLE character (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES "user"(id),
  name VARCHAR(50) NOT NULL,
  level INT DEFAULT 1,
  xp INT DEFAULT 0,
  strength INT DEFAULT 0,
  agility INT DEFAULT 0,
  vitality INT DEFAULT 0,
  luck INT DEFAULT 0,
  created_at TIMESTAMP DEFAULT NOW()
);
```

### ItemInstance

```sql
CREATE TABLE item_instance (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  owner_id UUID REFERENCES character(id),
  item_base_id VARCHAR(100) NOT NULL,
  rarity VARCHAR(20) DEFAULT 'common',
  upgrade_level INT DEFAULT 0,
  equipped_slot VARCHAR(50),
  created_at TIMESTAMP DEFAULT NOW()
);
```

### DungeonProgress

```sql
CREATE TABLE dungeon_progress (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  character_id UUID REFERENCES character(id),
  floor INT NOT NULL DEFAULT 1,
  phase INT NOT NULL DEFAULT 1,
  completed BOOLEAN DEFAULT FALSE,
  updated_at TIMESTAMP DEFAULT NOW()
);
```

### BattleRoom (Redis — efêmero)

```ts
export interface BattleRoom {
  id: string;
  type: '1v1';
  players: string[];         // characterId[]
  state: BattleState;
  createdAt: number;
  expiresAt: number;
}
```

## 5. WebSocket — Eventos

### Cliente → Servidor

| Evento | Payload | Descrição |
|---|---|---|
| `battle:join` | `{ characterId }` | Entrar na fila de matchmaking |
| `battle:action` | `{ type, angle, force, item? }` | Enviar ação do turno |
| `battle:reconnect` | `{ roomId, characterId }` | Reconectar a sala ativa |
| `battle:surrender` | — | Render |

### Servidor → Cliente

| Evento | Payload | Descrição |
|---|---|---|
| `battle:matched` | `{ roomId, opponent }` | Partida encontrada |
| `battle:state` | `BattleState` | Estado autoritativo |
| `battle:turn` | `{ playerId, timeLimit }` | Início de turno |
| `battle:result` | `{ winner, loser, xp, gold }` | Resultado final |
| `battle:error` | `{ code, message }` | Erro de ação |

---

## 6. Backend Autoritativo — Fluxo de Turno

```
1. Servidor recebe battle:action do jogador.
2. Valida ação (é o turno dele? Item está equipado?).
3. Calcula projétil com física autoritativa.
4. Aplica dano e atualiza TerrainState.
5. Verifica efeito rúnico.
6. Emite battle:state para ambos.
7. Troca turno, emite battle:turn para o próximo.
```

## 7. Reconciliação Cliente

```ts
// Cliente executa animação imediatamente (previsão local)
// Ao receber battle:state do servidor:
// - Se posição/dano coincide: mantém
// - Se diverge: corrige suavemente (lerp)
// - Se ação inválida (battle:error): desfaz animação e exibe mensagem
```

## 8. Matchmaking

- Fila Redis FIFO por modo de jogo.
- Ao entrar na fila, verifica se há adversário com força de combate ±20% do seu.
- Se não encontrar em 30s, abre para qualquer adversário.
- Cria `BattleRoom` no Redis com TTL de 1 hora.

---

## 9. Reconexão

- `BattleRoom` fica ativa por 60s sem o jogador.
- Ao reconectar com `roomId` válido e `characterId` autenticado, backend emite `battle:state` completo.
- Se o tempo passar, o jogador ausente perde.

## 13. Riscos

| Risco | Mitigação |
|---|---|
| Latência WebSocket ruim em mobile | Reconexão automática + timeout generoso |
| Divergência entre física local e servidor | Usar mesma lib TypeScript pura nos dois lados |
| Banco sem índices causando lentidão | Indexar `user_id`, `character_id` nas migrations |
| Redis vazio após restart | Partidas em andamento são efêmeras — aceitável para MVP |
