# Spec de Implementação — Motor de Jogo Autoritativo no Backend (v1.8.0)

## 1. Resumo

Migrar toda a lógica crítica de partida para o backend (NestJS + WebSocket), tornando o servidor a única fonte de verdade sobre o estado da batalha. O cliente passa a ser uma camada de apresentação pura: recebe resultados do servidor e anima o que foi computado. Cobre todos os modos: PvP, Dungeon e vs CPU.

---

## 2. Pedido Original

> "Para a próxima implementação no v1.8.0 quero que todas as partes mais importantes da partida sejam calculadas e validadas no backend, cálculo de trajetória, física, estado atual do mapa (para saber onde foi escavado), posição dos players, itens, consumíveis e todo resto para garantir que o cliente não tenha como roubar o jogo."

---

## 3. Problema a Resolver

Hoje toda a lógica de batalha roda no cliente (Phaser/BattleScene):

- **Física do projétil**: `ProjectilePhysics` calcula trajetória localmente
- **Dano**: `DamageCalculator` decide quanto HP o inimigo perde
- **Terreno**: `TerrainEngine` mantém o estado de escavação client-side
- **HP**: Cada cliente mantém seu próprio HP sem validação
- **Turno**: Cliente decide quando o turno acabou
- **Vento**: `WindSystem` roda no cliente
- **Consumíveis e itens**: `ConsumableSystem` valida apenas client-side
- **IA**: `AiDecisionMaker` roda no cliente (vs CPU e Dungeon)

O atual `BattleGateway` recebe `{ angle, force }` e aplica um `calcDamage` aleatório sem física real — é só um placeholder. Qualquer jogador pode interceptar a requisição WebSocket e enviar valores forjados.

---

## 4. Objetivo da Implementação

1. Servidor computa toda lógica de partida (física, dano, terreno, HP, turno, IA)
2. Cliente envia apenas intenções: `{ ação, ângulo, força, posição }` — sem calcular resultados
3. Servidor valida e devolve o resultado completo: trajetória, impacto, dano, novo estado
4. Cliente usa resultado recebido apenas para animar — não infere nada por conta própria
5. Violações são registradas; acúmulo de N violações gera penalidade

## 6. Pesquisa e Referências

### O que foi pesquisado
- Arquitetura servidor-autoritativa para jogos multiplayer (Gabriel Gambetta — Client-Server Game Architecture)
- Anti-cheat para jogos turn-based via WebSocket (GameDev.net, Justia Patent US20130053150)
- Implementação de lobby multiplayer com NestJS (riven.ch, tempmail.us.com)
- Modelo Worms-like (turno com física determinística de projétil)

### Pontos relevantes encontrados
- **Modelo autoritativo puro**: Servidor é a única fonte de verdade. Cliente envia inputs, servidor retorna estado completo. Sem predição client-side para lógica de jogo.
- **Moves are atomic**: Uma ação inválida não causa nenhuma mudança de estado (sem rollback parcial).
- **Validação de input via DTO**: NestJS valida payloads WebSocket via class-validator antes de qualquer processamento.
- **Namespace por sessão**: Cada sala de batalha deve ser um room Socket.io isolado.
- **Terrain delta**: Enviar apenas `{ cx, cy, radius }` da explosão ao invés do bitmap completo.

### O que será aproveitado
- Modelo de `GameEngineService` autoritativo com pipeline: validar → simular → aplicar → broadcast
- Delta de terreno como eventos de escavação (não snapshot)
- Registro cumulativo de violações sem punição imediata

### O que foi descartado e por quê
- **Client-side prediction**: Desnecessário para jogo turn-based (baixa frequência de ações, tolerância de latência alta)
- **Snapshot completo do terreno**: 6,3 MB por broadcast seria inviável. Delta de explosões é suficiente.
- **Bibliotecas de física externas** (Matter.js, Rapier): O motor de física custom do projeto é determinístico e já está testado. Portar é mais seguro que substituir.

## 7. Decisões Tomadas

| Decisão | Escolha | Razão |
|---|---|---|
| Escopo de modos | Todos (PvP, Dungeon, vsAI) | Garantir integridade em qualquer modo |
| Resposta a ação inválida | Registrar + acumular (N→penalidade) | Evitar punição por lag; falsos positivos viram dados |
| Sync do terreno | Backend autoritativo + deltas | Mais seguro; evita tráfego de bitmap |
| Compartilhamento de código | Copiar para `backend/src/game-engine/` | Evita complexidade de monorepo com workspace |
| Terreno no backend | Carregar PNGs com `sharp` no startup | Não depende de Phaser |
| IA no backend | Portar `AiDecisionMaker` + `AiStrategyEngine` | vsAI e Dungeon também sob controle servidor |

## 10. Regras de Negócio

**RN01** — O servidor é a única autoridade sobre HP, posição validada, vento, turno e resultado de física.

**RN02** — O cliente NÃO decide se acertou o inimigo. O servidor calcula o ponto de impacto e comunica quem tomou dano.

**RN03** — Uma ação recebida fora de turno é ignorada e registrada como violação.

**RN04** — Uma posição reportada pelo cliente com desvio > 80px da última posição validada pelo servidor é ignorada; o servidor usa a última posição conhecida.

**RN05** — Força (`force`) deve estar entre 5 e 100. Ângulo (`angle`) dentro dos limites da arma. Valores fora do range são registrados como violação.

**RN06** — Consumível só pode ser usado uma vez por partida; o servidor mantém a lista de consumíveis já usados.

**RN07** — Ao acumular 3 violações, o servidor passa o turno do infrator automaticamente. Ao acumular 6, o infrator é declarado perdedor.

**RN08** — Terreno: o servidor mantém o bitmap de escavação. Quando uma explosão ocorre, o servidor aplica o buraco e emite um delta `{ cx, cy, radius }` para todos os clientes na sala.

**RN09** — Vento é gerado pelo servidor no início de cada turno. O cliente não pode influenciar o vento.

**RN10** — Em modo vsAI e Dungeon, o servidor computa a ação da IA após o turno do jogador, sem aguardar nenhum input do cliente.

**RN11** — Status effects (FREEZE, WEAK_SHOT, ITEM_BLOCK) são rastreados no servidor e aplicados antes de processar ações.

### Pipeline da ação no `GameEngineService`

```typescript
async processAction(roomId: string, characterId: string, dto: BattleActionDto): Promise<ActionResult> {
  const state = this.getState(roomId);

  // 1. Validar turno
  if (state.currentTurnPlayerId !== characterId) {
    return this.recordViolation(state, characterId, 'NOT_YOUR_TURN');
  }

  // 2. Validar status effects (FREEZE bloqueia shoot)
  if (dto.type === 'shoot' && state.getPlayer(characterId).statusEffects.has('FREEZE')) {
    return this.skipTurnWithViolation(state, characterId, 'FREEZE_BLOCK');
  }

  // 3. Validar inputs numéricos
  const validation = this.actionValidator.validate(dto, state);
  if (!validation.ok) {
    return this.recordViolation(state, characterId, validation.reason);
  }

  // 4. Validar posição (RN04)
  const player = state.getPlayer(characterId);
  const reportedX = dto.playerX ?? player.x;
  if (Math.abs(reportedX - player.x) > POSITION_TOLERANCE_PX) {
    this.recordViolation(state, characterId, 'POSITION_MISMATCH');
    // usa posição do servidor, não rejeita a ação
  }

  // 5. Executar ação
  switch (dto.type) {
    case 'shoot': return this.executeShoot(state, characterId, dto);
    case 'move':  return this.executeMove(state, characterId, dto);
    case 'use_consumable': return this.executeConsumable(state, characterId, dto);
    case 'pass_turn': return this.executePassTurn(state, characterId);
  }
}
```

### Terrain Engine no backend

O `TerrainEngine` do frontend é baseado em bitmap `Uint8Array`. No backend:

- **Startup**: Carregar PNGs de terreno com `sharp` e converter em `Uint8Array` (`TerrainLoader`)
- **Estado por sala**: Cada `ServerBattleState` mantém uma cópia independente do `Uint8Array`
- **Escavação**: `terrain.excavate(cx, cy, radius)` modifica o array in-place
- **Delta**: Retornar `{ cx, cy, radius }` ao invés do array completo

```typescript
// terrain-loader.ts
import sharp from 'sharp';

export async function loadTerrainBitmap(mapName: string): Promise<Uint8Array> {
  const path = `assets/maps/${mapName}/terrain.png`;
  const { data, info } = await sharp(path).raw().toBuffer({ resolveWithObject: true });
  // Converter RGBA → TerrainMaterial (usando canal alpha e cor para determinar material)
  return convertToTerrainMaterial(data, info.width, info.height);
}
```

## 17. Permissões e Segurança

- Todas as ações WebSocket validadas via DTO com `class-validator` antes de entrar no pipeline
- `characterId` extraído do `client.data` (autenticado via JWT no handshake) — nunca do payload
- Violações logadas com timestamp, tipo e contexto do estado no momento

- Terreno nunca é recebido do cliente; apenas lido do servidor

## 19. Tratamento de Erros

| Cenário | Comportamento |
|---|---|
| Ação com força inválida (ex: 150) | Registrar violação; clampar para 100 na primeira ocorrência |
| Ângulo fora do range da arma | Registrar violação; usar ângulo clamped |
| Consumível já usado | Rejeitar silenciosamente; emitir `battle:violation` |
| Desconexão durante animação | Timer de 60s; se não reconectar, derrota por abandono |
| Terreno PNG não encontrado no backend | Fallback: TerrainEngine vazio (sem material) + log crítico |
| `sharp` falha ao carregar PNG | Log de erro + usar mapa procedural como fallback |
| IA não consegue calcular ação | Passar turno da IA com log de aviso |

## 21. Suporte e Operação

**Como identificar que o motor autoritativo está sendo usado:**
- Log `[GameEngine] Partida iniciada` no backend ao entrar no `battle:active`

**Problemas comuns:**
- `sharp` não instala em Linux arm → substituir por `@napi-rs/canvas` ou pré-converter PNGs em build step
- Cliente animando na ordem errada → verificar se `battle:action_result` é emitido antes de `battle:ai_action`
- Terreno dessincronizado → garantir que deltas de reconexão incluem histórico de escavações da partida

**Mensagens de erro conhecidas:**
- `battle:error { code: 'NO_ROOM' }` — jogador não está em sala ativa
- `battle:violation { reason: 'NOT_YOUR_TURN' }` — ação fora de turno
- `battle:violation { reason: 'MAX_VIOLATIONS' }` — jogador punido com derrota

## 24. Riscos

| Risco | Probabilidade | Impacto | Mitigação |
|---|---|---|---|
| `sharp` incompatível no ambiente de deploy | Média | Alto | Testar no ambiente de deploy cedo; manter `@napi-rs/canvas` como alternativa |
| Latência percebida aumenta (animação espera servidor) | Alta | Médio | Animar imediatamente com path local (preview) e corrigir ao receber server; aceitável para turn-based |
| `TerrainEngine` diverge entre frontend/backend após port | Média | Alto | Criar teste que compara output: `TerrainEngine(frontend).excavate()` === `TerrainEngine(backend).excavate()` com mesmos inputs |
| IA trava o event loop do NestJS durante cálculo | Baixa | Alto | Executar cálculo de IA em `setImmediate` ou worker thread se demorar > 50ms |
| Memória: bitmap 6,3MB × N salas simultâneas | Baixa | Médio | Limite de salas ativas; limpar estado ao finalizar partida |
| Falsos positivos de violação por lag | Média | Médio | Tolerância generosa (±80px); banimento apenas em N=6; log para revisão |

## 25. Critérios de Aceite

- [ ] **CA01**: Em PvP, cliente A não pode influenciar HP ou terreno sem que o servidor processe e valide a ação
- [ ] **CA02**: Enviar `force: 9999` via WebSocket não causa dano anormal
- [ ] **CA03**: Enviar `battle:action` fora do próprio turno não causa nenhuma mudança de estado
- [ ] **CA04**: Terreno escavado por jogador A aparece idêntico no cliente de jogador B
- [ ] **CA05**: Em vsAI e Dungeon, a IA executa sua ação inteiramente no servidor sem input do cliente
- [ ] **CA06**: Reconexão dentro de 60s restaura estado completo (HP, posição, terreno escavado)
- [ ] **CA07**: Trajectory preview visual funciona sem enviar nada ao servidor
- [ ] **CA08**: Modo playground (BootScene) continua 100% client-side, sem WebSocket
- [ ] **CA09**: Acumular 3 violações resulta em turno passado; 6 violações resultam em derrota declarada
- [ ] **CA10**: Performance: pipeline de ação (validar + simular + broadcast) < 100ms no servidor
