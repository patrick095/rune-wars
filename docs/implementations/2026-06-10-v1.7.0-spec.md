# Spec de Implementação — v1.7.0: Inventário Real + Cofre + Admin Panel + Sala PvP Redesenhada

---

## 1. Resumo

Quatro grandes entregas na versão 1.7.0:

1. **Inventário funcional com dados reais** — inventário carrega `ItemInstance`s do backend com catálogo de definições, equipar/desequipar com feedback visual correto.
2. **Cofre/baú funcional** — tela dedicada do cofre exibe apenas cofre + inventário, permite arrastar itens entre ambos.
3. **Admin Panel (tecla "I" no Hub)** — painel acessível somente para admin no hub para inspecionar e editar inventário de qualquer player.
4. **Tela de Sala PvP redesenhada** — UI fiel à imagem de referência com seleção de equipe (4 slots), seleção de mapa por carrossel com thumbnail, seleção de modo de batalha, consumíveis como segundo inventário persistente, e 5 slots de seleção de consumíveis (repetíveis).

---

## 2. Pedido Original

> "Quero que faça toda a parte do inventário funcionar corretamente na versão 1.7.0, exibindo os itens que player realmente tem no inventário, podendo equipar certinho. Quero também que o cofre/bau funcione corretamente, quando for para o cofre vai aparecer somente o cofre e os itens do inventário podendo mover os itens para ali. Quero uma funcionalidade onde posso escolher um player e verificar o inventário dele e adicionar qualquer item ao inventário (função tipo admin), ela deve ser acessada somente no hub apertando o botão 'I' no teclado. Quero que você planeje toda a implementação da tela da sala na arena pvp baseada na imagem [...] os itens consumíveis vai ser como se fosse um segundo inventário do player pois o que ele tiver vai ficar com ele, quando consumir deve sumir dali, ele vai poder selecionar os consumíveis que quiser, inclusive vai poder repetir os consumíveis."

---

## 3. Problema a Resolver

### Inventário
- `InventoryService` do frontend chama `/api/inventory-slots/character/${id}/items` — endpoint que **não existe**. O endpoint real é `GET /api/characters/:id/inventory` (retorna `ItemInstance[]`).
- `ItemInstance` só tem `item_base_id`, `rarity`, `upgrade_level`, `equipped_slot` — sem `name`, `icon`, `description`, `category`. Não existe um `ItemCatalog` no backend.
- A tela de equipamentos (`EquipmentSlotsComponent`) não faz chamada de equip real — o `onDrop` no equipment slot está vazio.
- Equipar via frontend usa `POST /api/inventory-slots/character/:id/equip` que também não existe. O endpoint real é `PUT /api/characters/:id/inventory/:itemId/equip`.

### Cofre
- A aba Cofre aparece junto com Personagem e Inventário no `CharacterComponent`. O usuário quer que o cofre tenha uma tela separada — exibindo somente o baú + inventário, sem a aba de personagem.
- O backend do cofre está completo e funcionando.
- O frontend `VaultGridComponent` existe mas não está conectado corretamente ao `VaultService`.

### Admin Panel
- Não existe. Precisa ser criado do zero.
- Não existe campo `is_admin` na entidade `User`.

### Sala PvP
- A tela atual é minimalista: 2 slots de jogador, um `<select>` de mapa, 2 botões de ação.
- Precisa ser completamente redesenhada para 4 slots de equipe, seleção de mapa por carrossel com thumbnail de background, seleção de modo, inventário de consumíveis do player, e 5 slots de seleção de consumíveis (repetíveis).
- Consumíveis precisam ser persistentes por personagem (novo sistema de inventário de consumíveis no backend).

## 4. Objetivo da Implementação

1. Corrigir mapeamento frontend → backend do inventário (endpoint + serialização).
2. Criar catálogo de itens (`ItemCatalog`) como seed no banco e como constante compartilhada no frontend.
3. Fazer equip/unequip funcionar de ponta a ponta.
4. Criar rota/tela dedicada para o Cofre no Angular.
5. Criar `AdminInventoryPanelComponent` acessível via tecla "I" no Hub (somente admins).
6. Adicionar `is_admin` no `User` e endpoints admin protegidos.
7. Redesenhar `PvpRoomComponent` e `pvp-room.component.html` conforme imagem de referência.
8. Criar sistema de inventário de consumíveis por personagem (backend + frontend).

## 5. Contexto do Projeto

- **Stack:** Angular 17 + Phaser 3.80+ (frontend), NestJS + PostgreSQL + Redis (backend).
- **Padrão de tela:** Canvas único sem navegação Angular — sobreposições Angular via overlay system no `AppComponent`. A tela de cofre será um overlay Angular, não uma rota nova separada.
- **Inventário atual:** `ItemInstance` (backend) com `item_base_id` como string livre — não há tabela `item_catalog` no banco. Catálogo é implícito (referenciado em receitas de craft e listings do mercado).
- **Consumíveis atuais:** `ConsumableSystem` é estático — 5 tipos fixos definidos em `consumable-system.ts`. Não há persistência por personagem.
- **Assets disponíveis:** `assets/items/consumables/` tem PNGs para teleport, heal, ice-throw, invisibility, calibration-shot. `assets/maps/*/background.png` disponível para thumbnails.
- **Rotas PvP existentes:** `pvp-lobby` e `pvp-room` (gerenciadas pelo `GameNavigatorService`).
- **Padrão admin:** Não existe — será introduzido por campo `is_admin: boolean` na entidade `User`.

## 6. Pesquisa e Referências

### O que foi pesquisado
- Padrões de inventário em MMORPGs 2D (WoW, Gunbound, DDTank, Tibia)
- Abordagens de catálogo de itens: DB table vs. seed vs. JSON estático
- Angular DnD (CDK Drag and Drop) para inventário
- Telas de lobby PvP em jogos mobile (Clash Royale, Brawl Stars, Gunbound Mobile)
- Padrões de admin panel em jogos — acesso por flag vs. role

### Pontos relevantes encontrados

**Catálogo de itens:**
- A abordagem mais simples para projetos pequenos: JSON estático versionado no frontend + seed no banco. Evita migrations complexas cada vez que um item é adicionado.
- O `item_base_id` já é uma string livre — o catálogo é naturalmente desacoplado da instância.

**Consumíveis persistentes:**
- Em jogos como Gunbound/DDTank, consumíveis são comprados na loja e ficam no inventário. Ao entrar em uma sala, o jogador seleciona quais quer levar. Ao usar durante a partida, a quantidade decresce.
- A seleção da sala pode permitir repetição do mesmo consumível (ex: 5 poções de cura selecionadas) — cada slot é independente.

**Admin Panel:**
- Campo booleano `is_admin` é suficiente para MVP. Role system completo seria over-engineering para este estágio.
- A checagem deve ser feita no backend, não só no frontend.

**Tela de Sala PvP:**
- Layout da imagem de referência: duas colunas (equipe + consumíveis à esquerda, mapa + modo à direita).
- Background com textura de taverna medieval escura — usar `assets/hub/hub_background_painted.png` como base ou gerar novo asset.
- Thumbnail de mapa: fatia do `background.png` do mapa selecionado (já disponível em `assets/maps/`).

### O que será aproveitado
- `VaultService` backend — completo, só precisa correção de integração no frontend.
- `VaultGridComponent` — reutilizar na tela dedicada de cofre.
- `InventoryGridComponent` e `ItemSlotComponent` — reutilizar na tela de cofre e na sala PvP.
- Assets de consumíveis em `assets/items/consumables/` e `assets/rune-wars/items/consumable/`.
- `background.png` dos mapas para thumbnails.

### O que foi descartado e por quê
- **Role system completo (RBAC):** overkill para MVP admin. `is_admin: boolean` é suficiente.
- **Catálogo em tabela DB separada:** desnecessário neste estágio — JSON estático versionado é mais simples de manter.
- **Drag-and-drop CDK completo:** o `ItemSlotComponent` já tem DnD — reutilizar.
- **WebSocket para sala PvP:** continua com polling de 3s como já implementado.

## 7. Decisões Tomadas

| # | Decisão | Justificativa |
|---|---------|---------------|
| D1 | Catálogo de itens como `ITEM_CATALOG` — constante TypeScript compartilhada no frontend, seed SQL no backend | Evita migration nova toda vez que item é adicionado |

| D8 | PvP room: 4 slots de time (1 por time, 4 times) em slot único (não 2 times de 4) | Conforme a imagem: 4 slots numerados 1–4 em "SUA EQUIPE" |

## 10. Regras de Negócio

### Inventário
- RN01: Exibir apenas itens que o personagem ativo realmente possui no banco (`ItemInstance.owner_id = characterId`).
- RN02: O ícone, nome, categoria e descrição de um item são resolvidos pelo `ITEM_CATALOG` via `item_base_id`.
- RN03: Equipar um item de `category: 'weapon'` ocupa o slot `mainHand`; `secondary` → `offHand`; `armor` → `chest`; `accessory` → `accessory1` ou `accessory2` (primeiro livre); `head` → `head`; `legs` → `legs`.
- RN04: Só pode haver 1 item equipado por slot. Equipar em slot ocupado substitui o anterior (desequipa o anterior, equipa o novo).
- RN05: Item equipado fica marcado como `equipped_slot != null` no banco.

### Cofre
- RN06: Depositar item remove do inventário do personagem e adiciona ao slot do cofre. Taxa: zero (o backend cobra na retirada).
- RN07: Retirar item custa 100 gold do personagem. O backend já implementa isso.
- RN08: A tela de cofre exibe SOMENTE o cofre e o inventário do personagem — sem abas de personagem, sem atributos.

### Admin Panel
- RN09: Admin Panel só é exibido se `currentUser.is_admin === true` (verificado via resposta do backend, não só localStorage).
- RN10: Admin pode adicionar qualquer item do catálogo ao inventário de qualquer personagem (sem custo de gold).
- RN11: Admin pode ver o inventário de qualquer personagem, mas NÃO pode removê-los (somente adição).
- RN12: O endpoint admin exige JWT válido + `is_admin: true` no payload.

### Consumíveis Persistentes
- RN13: Cada personagem tem um estoque de consumíveis em `character_consumable`. Campos: `character_id`, `consumable_id`, `quantity`.
- RN14: A seleção de consumíveis na sala tem 5 slots. Cada slot é independente — o mesmo consumível pode aparecer em múltiplos slots.
- RN15: Ao usar um consumível na batalha, a quantidade em `character_consumable` é decrementada em 1.
- RN16: Se a quantidade chegar a 0, o item some do inventário de consumíveis.
- RN17: Para testes, o admin panel pode adicionar consumíveis ao personagem.

### Sala PvP
- RN18: O dono da sala pode fechar uma vaga vazia clicando nela (slot passa de "Aguardando Jogador" para "Fechado").
- RN19: O dono pode reabrir uma vaga fechada clicando nela novamente.
- RN20: O dono pode chutar um jogador clicando no slot ocupado (aparece modal de confirmação com opção "Chutar").
- RN21: A seleção de modo de batalha (Rankeada, Livre, Guilds) é visual na v1.7.0 — "Batalha de Guilds" aparece desabilitado se o personagem não tem guild.
- RN22: O botão "PRONTO" substitui os botões atuais "Jogar vs CPU" e "Aguardar Jogador".

## 11. Fluxo do Usuário

### Inventário
1. Player acessa a tela de Personagem → aba "Inventário".
2. Sistema carrega `GET /api/characters/:id/inventory` → lista de `ItemInstance`.
3. Para cada item, resolve nome/ícone/categoria via `ITEM_CATALOG[item_base_id]`.
4. Player clica em um item não equipado → aparece tooltip com opção "Equipar".
5. Sistema chama `PUT /api/characters/:id/inventory/:itemId/equip` com `{ slot }`.
6. Slot de equipamento atualiza visualmente.
7. Player clica em item equipado no slot → opção "Desequipar".
8. Sistema chama `PUT /api/characters/:id/inventory/:itemId/equip` com `{ slot: null }` (unequip endpoint).

### Cofre
1. Player acessa o POI de Cofre no Hub (ou aba Cofre no CharacterComponent é substituída por overlay dedicado).
2. `GameNavigatorService` navega para `GameScreen: 'vault'`.
3. Overlay `VaultScreenComponent` é exibido: lado esquerdo = inventário 6×6, lado direito = cofre 6×10.
4. Player arrasta item do inventário para slot do cofre → `POST /api/vault/deposit/item`.
5. Player arrasta item do cofre para inventário → `POST /api/vault/withdraw/item` (cobra 100g).
6. Confirmação de taxa de retirada antes de executar.

### Admin Panel
1. Player admin está no Hub → pressiona "I" no teclado.
2. `HubComponent` detecta keydown, verifica `is_admin` → abre `AdminInventoryPanelComponent` como overlay.
3. Painel exibe lista de personagens (busca via `GET /api/admin/characters`).
4. Admin seleciona um personagem → vê inventário atual.
5. Admin seleciona item do catálogo (dropdown por categoria) e quantidade → clica "Adicionar".
6. Sistema chama `POST /api/admin/characters/:id/inventory/add` com `{ item_base_id, quantity }`.
7. Feedback de sucesso/erro.

### Sala PvP
1. Player cria/entra em uma sala → navega para `pvp-room`.
2. Nova tela exibe layout da imagem: equipe (4 slots) à esquerda, mapa + modo à direita.
3. Abaixo dos slots de equipe: seção "Consumíveis Selecionados" (5 slots) e "Inventário de Consumíveis".
4. Player clica em um consumível do inventário → vai para o próximo slot livre de seleção.
5. Player clica em um slot de seleção já preenchido → remove o consumível.
6. Mesmo consumível pode ser adicionado várias vezes (slots independentes).
7. Dono clica em slot vazio → modal "Fechar vaga / Cancelar".
8. Dono clica em slot com player → modal "Chutar jogador / Cancelar".
9. Dono altera mapa via carrossel (← →) → thumbnail atualiza com background do mapa.
10. Player clica em "PRONTO" → estado `ready` é enviado ao servidor.

### 13.2 Entidade: `character_consumable` (nova)

**Arquivo:** `system/backend/src/inventory/character-consumable.entity.ts`

```typescript
@Entity('character_consumable')
export class CharacterConsumable {
  @PrimaryGeneratedColumn('uuid')
  id: string;

  @Column()
  character_id: string;   // FK para character.id

  @Column()
  consumable_id: string;  // id do ConsumableSystem (ex: 'heal', 'teleport')

  @Column({ default: 0 })
  quantity: number;

  @CreateDateColumn()
  created_at: Date;
}
```

Migration:
```sql
CREATE TABLE character_consumable (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  character_id UUID NOT NULL REFERENCES character(id) ON DELETE CASCADE,
  consumable_id VARCHAR(50) NOT NULL,
  quantity INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(character_id, consumable_id)
);
```

## 19. Tratamento de Erros

| Situação | Comportamento |
|----------|---------------|
| `item_base_id` não encontrado no `ITEM_CATALOG` | Exibir item com nome "Item Desconhecido" e ícone placeholder |
| Backend inventory offline | Manter fallback mock existente no `InventoryService` |

## 21. Suporte e Operação

- **Para identificar problema de inventário vazio:** verificar se `character_id` no JWT corresponde ao personagem esperado. Rodar `SELECT * FROM item_instance WHERE owner_id = '<characterId>'` no banco.
- **Para dar itens a um player em produção:** usar Admin Panel (tecla I no hub) com usuário admin.
- **Para dar consumíveis:** mesma rota do Admin Panel → seção consumíveis.
- **Se o cofre não abre:** verificar se `GameNavigatorService` tem o screen `'vault'` registrado.
- **Mensagens de erro conhecidas:** `"Vault slot is already occupied"` → slot de destino já tem item. `"Insufficient gold"` → personagem não tem 100g para retirada.

|-------|--------------|---------|-----------|
| `item_base_id` no banco não corresponde a nenhuma chave do `ITEM_CATALOG` | Alta (dados mock podem ter ids diferentes) | Médio (itens aparecem como "desconhecidos") | Adicionar fallback visual; normalizar ids no seed |
