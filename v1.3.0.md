# PARTE 1 — Seleção/Criação de Personagem

## 1. Resumo

Ao abrir o jogo após o login, o jogador deve escolher ou criar um personagem antes de acessar qualquer tela do hub. O personagem selecionado fica ativo na sessão e seus dados (stats, raça, inventário, progressão) são usados em PvP, dungeon, crafting e em todo o jogo.

---

## 2. Pedido Original

> "ao abrir o jogo deve primeiro selecionar um dos personagens criados ou criar um do zero, para utilizar os dados dele para participar de pvp, dungeon, ter os dados dele, inventário, e etc. só depois vai para o hub"

---

## 3. Problema a Resolver

Atualmente o jogo não tem fluxo de seleção de personagem:
- O login redireciona diretamente para `/hub`
- `CharacterComponent` usa `characterId = 1` hardcoded
- `InventoryService` usa `characterId: number = 1` hardcoded
- `PvpComponent` pede o ID manualmente via input de texto
- `CharacterStorageService` salva apenas um build no localStorage (não usa a API)
- A entidade `Character` no backend não tem campo `race`
- Não há limite de 5 personagens por usuário no backend

---

## 4. Objetivo da Implementação

1. Criar tela de seleção de personagem (`/character-select`) que aparece após o login se não houver personagem ativo
2. Permitir criar até 5 personagens por conta, com nome único (global) e raça obrigatória
3. Persistir o personagem ativo na sessão via `localStorage` (`rw_character_id`)
4. Usar os dados do personagem ativo em todo o jogo (inventário, stats, batalha, dungeon)

---

## 5. Contexto do Projeto

**Stack:** NestJS (backend) + Angular 17 standalone (frontend) + Phaser 3 (game)

**Backend — O que já existe:**
- `Character` entity: `id` (UUID), `user_id`, `name`, `level`, `xp`, `strength`, `agility`, `vitality`, `luck`, `gold`, `created_at`
- `CharacterController`: `GET /characters`, `POST /characters`, `GET /characters/:id`, `PUT /characters/:id`
- `CharacterService`: create, findByUser, findOne, update
- `User` entity relacionado com `OneToMany → Character`
- JWT guard (`JwtAuthGuard`) protegendo todos os endpoints

**Backend — O que falta:**
- Campo `race` na entidade `Character`
- Validação: nome globalmente único
- Validação: máximo 5 personagens por usuário
- Endpoint `DELETE /characters/:id`

**Frontend — O que já existe:**
- `ApiService`: wrapper HTTP genérico (`get`, `post`, `put`, `delete`)
- `authGuard` protegendo todas as rotas
- `CharacterComponent` em `/character` para edição de build
- `CharacterStorageService` (localStorage, single build `runewars_build`)
- `InventoryService` com `characterId = 1` hardcoded
- `PvpComponent` lê `rw_character_id` do localStorage (compatível com o novo fluxo)
- Assets de raça em `assets/characters/`: `human_idle.png`, `human_battle.png`, `dwarf_idle.png`, `dwarf_battle.png`, `elf_idle.png`, `elf_battle.png`
- `BattleScene` hardcoda `human_battle` para o jogador

## 6. Pesquisa e Referências

### O que foi pesquisado
- Padrões de tela de seleção de personagem em jogos (Gunbound, Tibia, Lost Ark, MapleStory)
- Padrões de guard em Angular para fluxos com múltiplas etapas de autenticação
- Boas práticas de nickname único global em jogos

### Pontos relevantes encontrados
- Jogos de arena/RPG separam "conta" de "personagem" — a conta tem login, o personagem tem identidade no jogo
- Nickname único global é padrão em MMOs e jogos PvP para evitar confusão na tabela de rankings
- Tela de seleção com cards visuais (raça + nome + level) é o padrão UX mais reconhecido
- Limite de slots (3–10) é padrão — previne farming de personagens e simplifica UX

### O que será aproveitado
- Backend `Character` já estruturado — apenas `race` e validações precisam ser adicionadas
- `rw_character_id` no localStorage já é lido por `PvpComponent` — compatível com o novo serviço
- Assets de raça já existem no projeto
- `authGuard` como modelo para criar `characterGuard`

### O que foi descartado e por quê
- Server-side session para personagem ativo: desnecessário para o escopo atual, localStorage é suficiente
- Criação de avatar customizável (cor, equipamento visual na seleção): fora do escopo desta feature

## 7. Decisões Tomadas

| Decisão | Escolha |
|--------|---------|
| Limite de personagens | Até **5** por conta |
| Persistência | **Backend API** (`/characters`) |
| Campos obrigatórios na criação | **Nome** (único globalmente, max 50 chars) + **Raça** |
| Pontos ao criar | Personagem criado zerado (todos atributos = 0), editado depois em `/character` |
| Contexto ativo | Persiste na sessão via `localStorage` (`rw_character_id`), até trocar manualmente |
| Unicidade de nome | **Globalmente único** (igual a MMOs/PvP — evita confusão em rankings) |
| Raças disponíveis | `human`, `dwarf`, `elf` (assets já existentes) |
| Deleção de personagem | **Permitida** — endpoint `DELETE /characters/:id` será criado |

## 8. Decisões Pendentes

Nenhuma. Todas as decisões foram tomadas pelo usuário ou resolvidas pelo padrão existente do projeto.

## 10. Regras de Negócio

1. Um usuário pode ter no máximo **5 personagens**
2. O nome do personagem deve ser **único globalmente** (não pode repetir entre jogadores)
3. Nome: mínimo 3 caracteres, máximo 50, sem caracteres especiais exceto `_` e `-`
4. Raça obrigatória: `human`, `dwarf` ou `elf`
5. Personagem criado com todos os atributos zerados (level 1, xp 0, strength/agility/vitality/luck = 0)
6. Ao fazer login, se `rw_character_id` no localStorage for válido e pertencer ao usuário, ele é automaticamente ativado (sem passar pela tela de seleção)
7. Se o `rw_character_id` salvo não existir ou não pertencer ao usuário, limpar e redirecionar para `/character-select`
8. A tela de seleção **sempre** aparece se não houver personagem ativo válido
9. O jogador pode trocar de personagem ativo a qualquer momento via hub (link "Trocar personagem")
10. Deletar um personagem que é o ativo limpa `rw_character_id` e redireciona para `/character-select`

## 11. Fluxo do Usuário

### Primeiro acesso (sem personagens)
```
Login → /character-select (lista vazia) → Clica "Criar Personagem"
→ Modal/tela de criação → Preenche nome + raça → Confirma
→ Personagem criado → Selecionado automaticamente como ativo
→ Redireciona para /hub
```

### Acesso com personagens existentes
```
Login → verifica rw_character_id no localStorage
→ Se válido: carrega personagem → /hub diretamente
→ Se inválido/ausente: /character-select
→ Clica em um personagem → Selecionado como ativo → /hub
```

### Troca de personagem (via hub)
```
Hub → "Trocar Personagem" → /character-select
→ Seleciona outro personagem → Remove rw_character_id anterior
→ Salva novo rw_character_id → /hub
```

### Deleção de personagem
```
/character-select → Card do personagem → "Deletar" (com confirmação)
→ DELETE /characters/:id → Remove da lista
→ Se era o ativo: limpa localStorage → permance em /character-select
```

### 13.3 Validações no `CharacterService`

**Arquivo:** `system/backend/src/character/character.service.ts`

```typescript
async create(userId: string, dto: Partial<Character>) {
  // Validação 1: limite de 5 personagens
  const count = await this.repo.count({ where: { user_id: userId } });
  if (count >= 5) throw new BadRequestException('Limite de 5 personagens atingido');

  // Validação 2: nome único global
  const exists = await this.repo.findOne({ where: { name: dto.name } });
  if (exists) throw new ConflictException('Este nome já está em uso');

  // Validação 3: raça válida
  const validRaces = ['human', 'dwarf', 'elf'];
  if (!dto.race || !validRaces.includes(dto.race)) {
    throw new BadRequestException('Raça inválida');
  }

  const char = this.repo.create({ ...dto, user_id: userId });
  return this.repo.save(char);
}
```

## 14. Frontend

### 14.1 `ActiveCharacterService` (novo)

**Arquivo:** `system/frontend/src/app/shared/services/active-character.service.ts`

```typescript
@Injectable({ providedIn: 'root' })
export class ActiveCharacterService {
  private readonly STORAGE_KEY = 'rw_character_id';
  private _character$ = new BehaviorSubject<Character | null>(null);

  readonly character$ = this._character$.asObservable();
  get character(): Character | null { return this._character$.value; }
  get characterId(): string | null { return this._character$.value?.id ?? null; }

  setActive(char: Character): void {
    this._character$.next(char);
    localStorage.setItem(this.STORAGE_KEY, char.id);
  }

  clearActive(): void {
    this._character$.next(null);
    localStorage.removeItem(this.STORAGE_KEY);
  }

  getSavedId(): string | null {
    return localStorage.getItem(this.STORAGE_KEY);
  }

  // Carrega do backend ao iniciar a app (chamado no authGuard ou AppComponent)
  async loadFromStorage(api: ApiService): Promise<boolean> {
    const id = this.getSavedId();
    if (!id) return false;
    try {
      const char = await firstValueFrom(api.get<Character>(`/characters/${id}`));
      this._character$.next(char);
      return true;
    } catch {
      this.clearActive();
      return false;
    }
  }
}
```

```typescript
export const characterGuard: CanActivateFn = async (route, state) => {
  const active = inject(ActiveCharacterService);
  const api = inject(ApiService);
  const router = inject(Router);

  if (active.character) return true;

  const loaded = await active.loadFromStorage(api);
  if (loaded) return true;
```

## 15. Banco de Dados

### Tabela `character` — Alterações

| Campo | Tipo | Alteração |
|-------|------|-----------|
| `name` | `VARCHAR(50) UNIQUE NOT NULL` | Adicionar `UNIQUE` |
| `race` | `VARCHAR(20) NOT NULL DEFAULT 'human'` | **Novo campo** |

### Migration

```sql
-- migration: add_race_and_unique_name_to_character
ALTER TABLE "character" ADD COLUMN "race" character varying(20) NOT NULL DEFAULT 'human';
ALTER TABLE "character" ADD CONSTRAINT "UQ_character_name" UNIQUE ("name");
```

### Impacto em dados existentes
- Personagens existentes receberão `race = 'human'` por default (migration não destrói dados)
- Nomes duplicados existentes: verificar antes de aplicar a constraint — executar query de diagnóstico:
  ```sql
  SELECT name, COUNT(*) FROM character GROUP BY name HAVING COUNT(*) > 1;
  ```
  Se existirem duplicados, renomear antes de aplicar a constraint.

## 17. Permissões e Segurança

- Todos os endpoints `/characters` já são protegidos por `JwtAuthGuard`
- O backend valida `user_id` em `findOne` e `update` — usuário não acessa personagens de outros
- Frontend: `characterGuard` impede acesso às telas sem personagem ativo
- Ao deletar: backend verifica `user_id` antes de remover
- Não expor dados de outros personagens no endpoint de verificação de nome único (retornar apenas `409 Conflict` sem detalhar qual usuário tem o nome)

## 19. Tratamento de Erros

| Situação | Backend | Frontend |
|----------|---------|----------|
| Nome já em uso | `409 Conflict: 'Este nome já está em uso'` | Mensagem inline no campo nome |
| Limite de 5 atingido | `400 Bad Request: 'Limite de 5 personagens atingido'` | Botão "Criar" desabilitado (frontend valida antes) |
| Raça inválida | `400 Bad Request: 'Raça inválida'` | Não deve acontecer (UI restringe opções) |
| Personagem não encontrado | `404 Not Found` | Limpar `rw_character_id` e redirecionar para `/character-select` |
| API indisponível | — | Mensagem de erro + botão "Tentar novamente" na tela de seleção |
| `rw_character_id` inválido | — | Silenciosamente limpar e redirecionar para `/character-select` |

# PARTE 2 — Melhorias de Controles e UX Mobile na BattleScene

## P2.1 Resumo

Melhorias de usabilidade na BattleScene focadas em três áreas: (1) navegação no mapa por arrasto (desktop e mobile), (2) controles de ângulo precisos com granularidade de 1° e comportamento correto de hold, (3) barra de força redesenhada com régua visual e marcador do último tiro, e (4) ângulos limitados por tipo de arma.

---

## P2.2 Pedido Original

> "caso o mapa seja muito grande e seja maior que a tela, ao clicar e arrastar consegue se mover no mapa, assim como no touchscreen no smartphone."
>
> "os botões para mudar o angulo está muito dificil, pois os botoe na tela so aumenta ou diminui de 5 em 5, o que deveria ser de um em 1 e ao cliar e segurar vai aumentando"
>
> "sobre os botoes do teclado com cliques rápidos está aumentando ou diminuindo muito o que dificulta ajustes finos."
>
> "Os botoes na tela so devem aparecer caso seja no mobile, e deve aparecer de forma que seja bem usável e não como está hoje, deve ser focado no ui/ux para mobile."
>
> "na barra de força deve ficar uma sombra (ou alguma marcação) de onde foi o ultimo tiro e o valor numerico não deve ser exibido deve estar dentro da barra marcações tipo uma regra com marcações numeradas de 10 em 10 até o 100 e pequenos traços para a distancia de 1 em 1 e um traço maior a cada 5 de força."
>
> "As armas devem ter angulos limitados, para a usabilidade delas ficar diferente das demais também."

---

## P2.3 Regras de Negócio

1. **Mapa navegável**: quando o mapa é maior que a viewport, o jogador pode arrastar a câmera clicando + arrastando (desktop) ou com um dedo (mobile). Durante o turno do jogador, arrastar não dispara/move o personagem.
2. **Botões de ângulo na tela**: visíveis **apenas em mobile** (detectar via `window.matchMedia('(pointer: coarse)')`). No desktop, controle é exclusivamente pelo teclado.
3. **Granularidade de ângulo**:
   - Clique único: ±1°
   - Hold (pressão contínua): inicia a mudança após 400ms, repete a cada 80ms
   - Teclado (`←`/`→`): ±1° por keydown; throttle de 100ms para evitar variação excessiva em keypresses rápidos consecutivos
4. **Barra de força**:
   - Sem valor numérico exibido externamente
   - Interior da barra tem marcações estilo régua: traços grandes numerados a cada 10 (10, 20, 30... 100), traços médios a cada 5, traços pequenos a cada 1
   - Marcador visual (ghost/shadow) da posição de força do último tiro, na cor da barra mas com 40% de opacidade
5. **Ângulos por arma**: cada tipo de arma define `minAngle` e `maxAngle`. O ângulo atual é clampado dentro desse range ao trocar de arma.

---

## P2.4 Feature: Navegação do Mapa por Arrasto

### Comportamento
- Disponível em **todo momento** (durante turno do jogador e da IA, fora de animações de tiro)
- Input desktop: `pointerdown` + `pointermove` + `pointerup` no canvas
- Input mobile: touch drag com 1 dedo
- A câmera não pode sair dos bounds do mapa (`setBounds` já configurado)
- Não interfere com seleção de ângulo/força nem com o movimento do personagem

### Implementação — `BattleScene`

```typescript
// Habilitar drag da câmera nativa do Phaser
this.cameras.main.setDrag(true); // não existe em Phaser — implementar manualmente

// Implementação manual
private isDraggingMap = false;
private dragStartX = 0;
private dragStartY = 0;
private cameraStartScrollX = 0;
private cameraStartScrollY = 0;

setupMapDrag(): void {
  this.input.on('pointerdown', (p: Phaser.Input.Pointer) => {
    if (p.button === 0 || p.wasTouch) {
      this.isDraggingMap = true;
      this.dragStartX = p.x;
      this.dragStartY = p.y;
      this.cameraStartScrollX = this.cameras.main.scrollX;
      this.cameraStartScrollY = this.cameras.main.scrollY;
    }
  });
  this.input.on('pointermove', (p: Phaser.Input.Pointer) => {
    if (!this.isDraggingMap || !p.isDown) return;
    const dx = this.dragStartX - p.x;
    const dy = this.dragStartY - p.y;
    this.cameras.main.setScroll(
      this.cameraStartScrollX + dx,
      this.cameraStartScrollY + dy
    );
  });
  this.input.on('pointerup', () => { this.isDraggingMap = false; });
}
```

**Conflito com câmera follow:** ao iniciar arrasto, suspender temporariamente o `startFollow`. Ao soltar, retomar o follow. Ou: usar follow apenas durante animações de tiro/movimento e liberar para arrasto livre no restante do turno.

```typescript
// No handler do botão de ângulo:
private holdTimer: ReturnType<typeof setTimeout> | null = null;
private holdInterval: ReturnType<typeof setInterval> | null = null;

onAngleButtonDown(delta: 1 | -1): void {
  this.changeAngle(delta); // imediato
  this.holdTimer = setTimeout(() => {
    this.holdInterval = setInterval(() => this.changeAngle(delta), 80);
  }, 400);
}

onAngleButtonUp(): void {
  if (this.holdTimer) { clearTimeout(this.holdTimer); this.holdTimer = null; }
  if (this.holdInterval) { clearInterval(this.holdInterval); this.holdInterval = null; }
}
```

```typescript
private lastAngleKeyTime = 0;

handleAngleKey(delta: 1 | -1): void {
  const now = Date.now();
  if (now - this.lastAngleKeyTime < 100) return;
  this.lastAngleKeyTime = now;
  this.changeAngle(delta);
}
```

## P2.7 Feature: Ângulos Limitados por Arma

### Definição

Cada arma tem um range de ângulo válido. Ao disparar ou ao trocar de arma, o ângulo atual é clampado.

```typescript
export interface WeaponAngleLimits {
  minAngle: number; // graus, ex: 10
  maxAngle: number; // graus, ex: 85
}

export const WEAPON_ANGLE_LIMITS: Record<string, WeaponAngleLimits> = {
  default:        { minAngle: 5,  maxAngle: 85 },  // canhão padrão
  mortar:         { minAngle: 45, maxAngle: 85 },  // só alto — arco elevado
  sniper:         { minAngle: 5,  maxAngle: 30 },  // só baixo — tiro reto
  grenade:        { minAngle: 30, maxAngle: 75 },  // ângulo médio-alto
  drill:          { minAngle: 5,  maxAngle: 45 },  // escavação diagonal
  bouncer:        { minAngle: 10, maxAngle: 80 },  // amplo
};
```

No `BattleScene.changeAngle()`:
```typescript
private changeAngle(delta: number): void {
  const limits = getWeaponAngleLimits(this.currentWeapon);
  this.currentAngle = Math.max(limits.minAngle, Math.min(limits.maxAngle, this.currentAngle + delta));
  this.updateAngleDisplay();
}
```

Ao trocar de arma, clampar o ângulo atual:
```typescript
private switchWeapon(weapon: string): void {
  this.currentWeapon = weapon;
  const limits = getWeaponAngleLimits(weapon);
  this.currentAngle = Math.max(limits.minAngle, Math.min(limits.maxAngle, this.currentAngle));
  this.updateAngleDisplay();
}
```
